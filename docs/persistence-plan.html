Persisting users & dashboards

better-auth + Drizzle + Neon Postgres. YNAB OAuth becomes a server-side sign-in provider — which means your YNAB connection itself finally persists across devices.

Auth  better-auth (drizzle adapter) DB  Neon Postgres Hosting  Vercel (unchanged)

01 The unlock better-auth gives us

Key discovery: YNAB supports the Authorization Code Grant — a server-side OAuth flow with a client secret and refresh tokens (access tokens expire every 2 hours, but refresh silently). Your .env already contains a YNAB client secret. better-auth's generic OAuth plugin can register YNAB as a first-class social provider using this flow.

This collapses "sign in" and "connect YNAB" into one flow: the existing "Sign in with YNAB" button keeps working — but now it creates a real account and links YNAB in a single redirect. better-auth stores the YNAB access + refresh tokens in its account table, the browser never sees them, and tokens refresh automatically server-side forever. The current implicit flow (token in URL fragment, localStorage, re-auth every session) gets deleted entirely.

03 Schema

better-auth generates its own Drizzle schema via its CLI (npx @better-auth/cli generate) — four core tables. We add exactly one table of our own. 

── generated by better-auth CLI, drizzle adapter (provider: "pg") ──
user           id (text pk) · name · email (unique, nullable) · emailVerified
               image · createdAt · updatedAt
               // YNAB's /v1/user exposes only an id — email/name stay null

session        id (text pk) · userId (fk) · token (unique) · expiresAt · ip · userAgent …

account        id (text pk) · userId (fk) · providerId · accountId (YNAB user id)
               accessToken · refreshToken · accessTokenExpiresAt · scope …
               // ← YNAB tokens live here; server refreshes them silently

verification   id · identifier · value · expiresAt …      // OAuth state / PKCE

── ours ──
dashboards     id (uuid pk) · userId (fk → user) · budgetId (text)
               charts (jsonb)      // ChartConfig[] — existing zod schema reused
               settings (jsonb)    // { weekStart } — future home for preferences
               createdAt · updatedAt
               // unique(userId, budgetId)

Charts stay JSONB because the app treats the dashboard as an atomic document (drag-reorder, bulk normalize, one Zod schema) and never queries individual charts. The existing chartConfigSchema (src/lib/app/chart-config.ts:63) remains the single source of truth and re-validates server-side on every write.

04 YNAB as a better-auth social provider

// src/lib/server/auth.ts
betterAuth({
  database: drizzleAdapter(db, { provider: "pg", schema }),
  plugins: [genericOAuth({ config: [ynabProvider] }), sveltekitCookies(getRequestEvent)],
  socialProviders: { /* optional 2nd provider — decision 02 below */ }
})
  • Sign in with YNAB → authClient.signIn.social({ provider: "ynab", callbackURL: "/app" }). Redirects to YNAB with response_type=code + scope=read-only (PKCE on by default, which YNAB supports).
  • Callback → better-auth exchanges the code server-side at app.ynab.com/oauth/token using the client secret, stores access + refresh tokens in account, upserts the user row (identity = YNAB user id from /v1/user), sets the session cookie, redirects to /app.
  • Every request → hooks.server.ts calls auth.api.getSession, populates event.locals; unauthenticated /app traffic redirects to landing.
  • Token refresh → the YNAB proxy checks accessTokenExpiresAt; when stale, exchanges the refresh token (grant_type=refresh_token) — no user interaction, ever.
  • Sign out → authClient.signOut() deletes the session. YNAB authorization is not revoked — next sign-in resumes the same account.
One-time YNAB app setting

The YNAB OAuth app's redirect URI must add /api/auth/callback/ynab (better-auth's convention). The existing /auth/ynab/callback page and all implicit-flow code (startYnabOAuth, readToken, sessionStorage state dance) get deleted. Also rename the YANB_CLIENT_SECRET typo → YNAB_CLIENT_SECRET.

05 New server surface

Everything the client calls is session-guarded JSON. YNAB data passes through but is never persisted. 

POST   /api/auth/*                  better-auth handler (mounted in hooks.server.ts)

GET    /api/ynab/budgets            → BudgetEntity[]          (replaces client-side ynabFetch)
GET    /api/ynab/snapshot?budgetId= → NormalizedBudgetData   (replaces fetchNormalizedBudgetSnapshot)

GET    /api/user-data/dashboard?budgetId=   → { charts, settings } | 404
PUT    /api/user-data/dashboard?budgetId=   ← zod-validated upsert
PATCH  /api/user-data/settings              ← { weekStart }

Client flow after the swap

  • Load /app → layout server-load resolves session + linked YNAB account. Dashboard loads from Postgres; YNAB snapshot loads from the proxy. If no YNAB account is linked (possible if a second sign-in provider is added later), show the existing connect panel.
  • Every edit → existing readDashboard/writeDashboard call sites swap to a new dashboard-repo.ts with the same API — debounced (≈500ms) PUT, optimistic UI. app-state.ts, local-user-data.ts and all token plumbing deleted.
  • Budget switch → fetches that budget's dashboard; svelte-query caching (already in place) handles it.
  • New device → sign in with YNAB → same user, dashboards/settings appear, YNAB connection live via stored refresh token. Zero re-setup. This is the whole point.

06 Decisions for you

Needs your call

1. Sign-in providers — YNAB only?

YNAB-only (recommended): one button, one flow, identity = YNAB. Every YNAD user is a YNAB user by construction.

Add GitHub/Google alongside: accounts independent of YNAB; they'd get an explicit "Connect YNAB" step (the old connect panel reborn as a settings action, since linking becomes authClient.linkSocial). More surface, but future-proof if YNAD ever supports other data sources.

Needs your call

2. First-login migration of localStorage data?

Recommended: on first authenticated load, if the server dashboard for the selected budget is empty and the local one isn't, upload it once, then clear local keys. Your current setup carries over automatically.

Alternative: server is immediately the only truth; you rebuild your dashboard once. Cleaner code, one-time pain.

Needs your call

3. Require sign-in for /app?

Recommended: yes — /app redirects unauthenticated visitors to the landing page. With server-side dashboards there's little meaning to a signed-out dashboard, and it removes the localStorage fallback code path entirely.

Alternative: keep a signed-out guest mode backed by localStorage; adds a merge story and a second code path to maintain.

Assumed — say if you disagree

4. YNAB calls move fully server-side

Required by the code-flow decision (only the server holds the token). Client-side ynabFetch/client.ts gets replaced by the proxy endpoints. Rate-limit handling (429 pause UX) moves into the proxy and is relayed to the client.

Migrations

Your own first login

Sign in with YNAB → new account row → empty server dashboard → one-time localStorage upload (decision 2) → done. Every device after that: just sign in.

Privacy & landing copy

"Stores nothing on any server" (src/routes/+page.svelte:108) and the settings-page copy get rewritten: we store your account identity, YNAB authorization, and dashboard configuration — never YNAB financial data. Privacy page and Terms get a matching pass. terms/+page.svelte and privacy/+page.svelte exist already.
